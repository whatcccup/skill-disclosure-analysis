# 技能解剖与渐进披露

把用户指定的 Skill 当作**分析对象**。用户要求完整交付时，制作一份按“总览 → 渐进披露树 → 方法与质检等补充分析”排列的 Markdown 主报告，另附可编辑的 draw.io 图及 SVG 预览；只要求理解或局部产物时按本轮范围收窄。不要把对原 Skill 的阅读误当成执行授权。

## 边界先行

- 以用户指定的 `SKILL.md` 和包内关联文件为证据范围；外部链接、另一个安装位置或同名版本，除非用户要求，不补入事实。引用的聊天只能提供核查线索，结论仍须回到指定文件核对。
- 区分**读取与分析**、**运行被分析 Skill**、**写分析产物**三种动作。按本轮授权分别处理；“先理解、不执行”不授权运行目标脚本、安装依赖、修改原包或配置。若用户同时禁止工具调用且未提供正文，只能请其粘贴内容。
- 只在用户要求制作或更新文件时写产物；放在用户指定位置，未指定时放在当前项目文件夹内的分析目录，不默认写进技能安装目录或原包。当前项目位置不明确时，先请用户给出分析输出目录。保留已有用户改动。

## 工作路线

1. **建立范围与证据索引。** 读取主 `SKILL.md` 的 frontmatter、正文标题、引用关系；按需只读关联的规则、脚本、Schema、示例和资源说明。记录缺失、版本分歧与无法读取的文件。分析脚本可以读源码，不运行目标业务逻辑。
2. **先写报告总览，再写渐进披露树。** 总览用简短段落交代 Skill 做什么、输出目标、触发条件和适用边界；用“输入 → 判断 → 执行 → 输出”概括整个流程，并说明 AI、脚本与人工各自负责什么、在哪里由人工确认。每项都回链来源，不能把推断写成已验证行为。其后以 `SKILL.md` 为披露树唯一主干，按原文顺序从 frontmatter 到末节；每节写含义、输入、判断、执行、输出及适用边界。把直接引用放到相应段落下，再展开关联文件内部的判断与流程。只在原文确有条件时画分支。标清“文档披露顺序”与“实际执行顺序”的区别。
3. **做可编辑图。** 先读[图与文件规范](../references/artifacts.md)。图的左侧放主干及缩进子步骤，右侧放判断路径和引用卡片；文件卡片写名称、完整的 Skill 根目录相对路径、**此处引用的具体作用**。同一文件在不同节点可有不同说明。原文明确要求用户输入的节点标红，并区分条件性先问与终版前必须确认。需要确定性生成时用 `../scripts/render_disclosure.py` 从核对过的 JSON 模型生成 `.drawio` 和 `.svg`；脚本只处理分析模型，不调用目标 Skill。
4. **在披露树后写补充分析。** 先读[证据与风险方法](../references/evidence.md)。按方法、质检、失败处理、证据位置、未知项和迁移风险收束主报告；引用前文节点而不重述流程。文档声明、代码可见行为与分析推断分别标明；没有证据就写“无法从文档确认”。用户要求独立信息包时，再把本部分另存，并与主报告互链。
5. **核验交付。** 检查图的 XML 可解析、draw.io 各节点可编辑、链接目标存在、Markdown 链接有效、章节与图节点一一对应。能目视预览时检查截断与交叉线；做不到就如实写明。不要把静态校验说成真实案件出图或目标编辑器验收。

## 默认交付语言与结构

默认中文标题，保留有识别价值的英文原词并在旁边给出中文含义，例如“意图识别（Intent Router）”。主报告固定顺序为**总览、披露树、方法与证据、质检与失败、未知项与迁移风险**；总览只给全局导航，不代替逐节拆解。图的根节点固定为 `SKILL.md`；编号跟随**分析顺序**，不要伪装成原文自带编号。HTML 只在用户明确需要网页浏览版本时追加。

## 本轮新增｜交付选择与披露图聚焦

进入解释阶段时，除非用户本轮已经明确指定交付程度，先通过可用的**用户输入弹窗**询问一次：“简单交付，还是完整交付？”选项写清：

- **简单交付：**在回复中说明技能用途、触发、边界、主流程、AI／人工分工和关键未知；不默认制作主报告或图。用户明确要求保存文件时按其范围写。
- **完整交付：**制作主报告 Markdown、可编辑 draw.io 披露树图及 SVG 预览，沿用上面的报告顺序与验收。

这是交付偏好选择，不是执行或写入授权。弹窗无回复、不可用或无法弹出时，**默认完整交付**；不要因等不到答复停住。用户已明确说“只解释几句”或“给完整报告和图”时按其请求直接执行，不重复弹窗。
若同时无法确定分析输出文件夹，可把路径问题放进同一次弹窗；交付程度无答复可默认完整，但路径未明确前仍不写分析文件。

披露树图只放**影响技能工作方式**的模块：触发、输入、判断、执行、输出、质检、确认、失败和必要引用。README、License、Changelog 等若只提供介绍、许可或版本历史，不作为工作流程节点或右侧文件卡；若其中确实承载操作规则，才摘取那条规则并说明其实际作用。被图省略不等于来源被忽略：许可或版本风险可在主报告的补充分析中简述并给证据位置。

每个图格先回答“**这个模块做什么，如何改变下一步工作**”。`含义`写核心职责或 `description` 的实际承诺，不写“本节声明了哪些 YAML 字段”一类目录式概括；字段名、作者、版本等只在它们影响触发、兼容性或判断时写入对应项。不要把没有源证据的“唯一依据”“必须”等绝对判断塞进格子。

原文列出具体口令、条件、选项或分支时，**逐项展开原文内容与对应效果**。例如原文给出四句中文触发口令，图格或子节点应分别写出四句及各自触发的工作，不能只写“四种中文口令”。卡片放不下时用子节点，不把字缩到不可读；实际词句不在来源中时写“无法从文档确认”，不要编造四句。生成图前先做一次“读者只看格子能否回答它做什么、有哪些分支”的检查。
