# Skill Disclosure Analysis｜技能解释、拆分与升级

这个技能把“看懂别人的 Skill → 挑出可迁移规则 → 嵌入自己的工作流”分成三个按需使用的子技能。入口为 [SKILL.md](SKILL.md)。原技能始终作为证据对象；阅读它不等于运行它。

| 阶段 | 什么时候用 | 结果 |
| --- | --- | --- |
| [解释](subskills/explain.md) | 需要弄懂指定 Skill 的结构与边界 | 弹窗选简版说明或完整主报告 Markdown＋draw.io／SVG；无回复默认完整。原有解释流程保留，并收紧图中工作节点 |
| [拆分](subskills/split.md) | 需要判断哪些作者规则值得迁移，以及下一步如何借用 | 四类取舍与学习动作、还原上下文的七字段映射、限定任务族的候选骨架 |
| [升级](subskills/upgrade.md) | 需要局部改造原技能，或重组规则形成新工作流 | 先选择起点并审查能力链／骨架到个人规则的映射与缺口；确认后生成技能并做真实任务演练 |

阶段**不会自动连续执行**。例如只问“这个 Skill 是做什么的”，不会顺手生成派生技能。升级阶段的信息不足时，先问关键缺口；用户确认改造方案后才写新 `SKILL.md`。三阶段通过证据链接和规则 ID 传递结论，避免重复抄写。

拆分阶段先解释原规则在什么输入下作什么判断、产生什么效果，再决定保留、改参数、排除或交人判断。骨架只服务于写明的任务族，是升级阶段要填入个人规则的底稿；“旧成果＋新材料”的增量更新骨架不自动适用于从零新建或其他语义提取任务。

升级有两条路线：**局部改造**直接从原 Skill 的目标能力分支及其依赖出发，例如保留案件时间轴的抽取和保真流程、修改版式与渲染；**工作流重组**才以拆分出的候选机制和适用骨架为起点。已有骨架不会强制缩窄原技能的目标能力。

**分析文件默认保存在当前项目文件夹**，不放进技能安装目录；项目归属或分析输出位置不明确时，先请用户指定目录。新生成的技能本体另按用户指定或平台约定安装。

## 文件结构

- `SKILL.md`：入口与阶段路由。
- `subskills/`：三个阶段的操作说明。解释阶段保留原流程，另加入用户确认的交付选择、图内容和分析归档规则。
- `references/`：原有披露图规范与证据方法；没有改写。
- `scripts/render_disclosure.py`：从人工核对的 JSON 模型生成 draw.io 和 SVG，不调用被分析 Skill。
- `harness/` 与 `scripts/run_harness.py`：阶段门槛、去重合同、回归情境及静态／绘图烟测。

## 验证

在本目录运行：

```bash
python3 scripts/run_harness.py
```

它会检查解释核心是否符合当前基准、三阶段文件与回归情境，并在临时目录测试绘图脚本。真实任务的事实、人工确认、目标编辑器显示与桌面操作仍需另行验收。新阶段的行为案例见 [Harness](harness/README.md)。

解释阶段的披露图只画影响技能工作方式的模块；普通 README、License、Changelog 不占节点。原文列出多条触发口令或分支时，图格逐项写明具体内容与效果，避免只写数量或字段清单。
