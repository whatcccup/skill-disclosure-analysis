# 披露树后半部：证据与风险

仅在写主报告的补充分析、独立解剖信息包，或核对文档／代码保证时读取。该部分接在披露树之后，不能重新抄一遍节点与流程。

## 接续前文

主报告前面的总览已经交代“目标、触发、适用边界、输入→判断→执行→输出、AI／脚本／人工分工”。这里直接展开披露树尚未充分说明的**方法、质检、失败、证据、未知与迁移风险**；需要回指时链接对应节点。只有另存独立信息包时，才在该文件开头放简短交叉索引。

## 证据用语

| 类别 | 写法 |
| --- | --- |
| 文档写明 | 指明 `SKILL.md` 或引用规则的文件和段落；这是设计声明，不自动证明实现。 |
| 代码可见 | 指明脚本、Schema、默认参数、异常分支或返回值；静态阅读不等于执行通过。 |
| 分析推断 | 同时给出支持推断的两侧证据，并说清还缺什么实测。 |
| 未知 | 固定写“无法从文档确认”，再说明缺运行结果、真实输入、用户答复或目标软件检查中的哪一种。 |

没有找到某项机制时，只能写“在**已检查的文件／入口中未发现**”，并列明搜索范围。不要把“未发现”说成全包绝对不存在。另一个聊天、README 宣传语或示例里的 `confirmed: true` 都不等于本次已核验的事实。

## 质检与失败矩阵

按关口列四列：**方法／可见检查、失败时的路径、自动机制能证明到哪里、人工还需核什么**。优先覆盖来源预检、语义提取、元素数量、字段合法性、确认状态、视觉检查、格式导出与回读。若目标 Skill 没有某个关口，写明缺口，不移植示例技能的机制。

检查“成功”一词的含义：如果可选导出、审计或 lint 的异常会被捕获并继续，仅以进程退出码不能证明全部文件成功；必须核对实际生成的清单和跳过信息。

## 风险登记

每条风险至少有：**冲突或缺口、两侧证据位置、迁移影响、验证或修复前提**。聚焦会改变工作决定的项目，例如文档与代码不同步、Schema 与示例不一致、人工确认缺凭据、格式各自重排、可选工具行为、分发版本与测试缺口。不要把某个样例包的缺陷预写成所有 Skill 的通病。

末尾列未知项和迁移前提，明确哪些只是建议，尚未获得修改或运行原 Skill 的授权。真实材料是否保真、目标软件能否正确打开、用户是否确实确认、测试宣称是否成立，都需要各自的证据；不能靠文档措辞推断。
