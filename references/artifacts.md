# 披露树与可编辑图的交付规范

仅在需要写 Markdown 树或绘图时读取。本规范描述产物，不是被分析 Skill 的运行规则。

## Markdown 披露树

- 正文最前放一段“技能总览”，概括用途与输出目标、触发和边界、全局输入→判断→执行→输出，以及 AI／脚本／人工角色。为每项附来源链接，未知项明示；总览不按段落重复整棵树。
- 标题以 `SKILL.md` 为根。第一层从 frontmatter 开始，按正文原有段落逐一排列；五步或多步主流程作为该段子节点缩进，不把所有文件平铺成另一条主干。
- 每个节点说明：**含义、输入、判断、执行、输出**。`含义`先写模块的实际职责或 `description` 的核心承诺，让读者只看该格就知道它做什么；不要用“列出 YAML 字段”“包含四种口令”等目录式概括代替内容。原文明确列出的口令、条件或选项要逐项写出其原文与效果；放不下时拆成子节点。没有某项时写“文档未说明”，不要补造。正文与脚本相互矛盾时并列说明，标注证据位置。
- 引用文件放在发生引用的节点下。先写为什么此处要读该文件，再写文件内部的输入、判断、执行、输出；不同位置重复引用同一文件时，解释该位置关注的不同章节或职责。
- 用 Skill 根目录相对路径显示文件，如 `/references/STANDARDS.md`、`/scripts/render.py`。Markdown 链接指向当前副本的真实文件；目录链接也要实际存在。
- 对需人工判断的条件显示“问谁、什么时候问、未回答能否继续草稿”。不要把可选征询、终版确认与中断式先问混为一种红色门禁。

## 图的结构

默认交付**可编辑 `.drawio`** 和配套 `.svg` 预览；SVG 不充当编辑源。用户指定其他可编辑格式时按其要求。图不采用品牌资源或复杂装饰，优先让层级和阅读路径清楚。

1. 左列按 `SKILL.md` 原文顺序对齐。主流程的 6.1、6.2 等子步骤缩进一档。每张主卡保留核心五项；内容长时拆行、增高，不缩到无法阅读。
   图只呈现影响技能工作的节点。README、License、Changelog 若仅是介绍、授权或版本历史，省略其节点和文件卡；若确有操作规则，摘出具体规则并标明作用。省略图节点时在分析模型中写明理由，不把图的节点数硬说成与主报告所有章节一一对应。
2. 右列对应当前节点的文件卡和条件分支。文件卡三行：**文件名**、`/references/...` 等完整相对路径、**此处要查的内容**。卡片可点击到本地副本。文件不存在时标“缺失”，不生成虚假链接。
3. 真正有条件选择的节点用菱形判断符号和分叉。分支标签写判断条件，终点写选择或要读的文件。未由资料支持的“先匹配者胜出”不可自行加上；规则冲突时写“需人工核定”。
4. 红色只标源文档明确要求用户输入的节点：区分“满足条件时先问”“标为终版前确认”“其他强制输入”。红色标签要有文字，不能只靠颜色表达。
5. 图顶注明“按文档披露顺序排列，不代表实际执行顺序”。若后段规则在前段工作中调用，直接注明交叉关系。
6. 中文标题优先；英文原名放括号里。文件名和代码字段保持原拼写，不翻译到失去可定位性。

## `render_disclosure.py` 的输入

脚本接收一个 UTF-8 JSON 文件和输出基名：

```bash
python3 scripts/render_disclosure.py model.json /path/to/output-base
```

必要顶层字段：`skill_root`（被分析包的绝对路径）、`sections`（按原文顺序的数组）。每个 section 有 `id`、`title`、`meaning`、`input`、`judgment`、`action`、`output`；可加：

- `level: 1`：相对主干缩进一档；默认 0。
- `refs`: `[{"path":"/references/X.md","use":"在此处核对……"}]`。
- `branches`: `[{"condition":"如果……","label":"结果名称","path":"/references/X.md","use":"该支查……"}]`；无文件的结果省略 `path`。
- `user_input`: `{"type":"conditional|before_final|required","label":"……"}`；只标有原文依据的要求。
- `details`: `[{"label":"触发口令 1","text":"原文口令及触发效果"}]`；原文列出若干口令／条件／选项而主卡需要逐项展示时使用。也可拆成 `level: 1` 子节点。
- `diagram: false` 与 `omission_reason`：该节仅属许可、简介、变更记录等非工作内容时，留在报告证据索引但不绘入图。没有具体理由不得省略工作规则。
- 引用项可设 `work_relevant: true`：README、License、Changelog 中确有工作规则且本处必须呈现时显式标记并写具体 `use`；否则绘图脚本默认不画这些文件卡。

模型文件是**已核对的分析结果**，不是自动从文档猜测出来的。生成器负责几何和图形；节点事实、引用条件和风险仍由分析者复核。

## 最小验收

- `.drawio`、`.svg` 均为合法 XML；主干、引用与分支在 draw.io 中是独立可编辑对象。
- 图内文件链接的目标实际存在，右卡显示完整相对路径；重复引用有逐节点用途。
- 红色提示有源文档证据；判断分支与原文条件一致；长字、卡片、边线无明显遮挡。
- 任取一张卡，只看卡中文字能说清模块职责；“四种口令”之类的计数必须有四个可核对的具体项，或注明原文未提供。无来源依据的“唯一”“必须”需删去或标成待核实。
- 如果只做静态 XML 与链接检查，没有在 draw.io 打开，应写“编辑器内视觉验收未完成”。
